# Runtime 连接稳定性独立工作包

状态：待诊断、待实现、待验收。本方案没有验证任何当前 llama.cpp 故障，也没有启动、关闭或重启现有服务。

## 边界

Alcor 不拥有 Stella 的 llama.cpp 进程。它只报告自己及决策后端的健康。llama.cpp 的启动、停止、重启归现有 Runtime/Corona/Nucleus 管理者，避免两个 supervisor 抢同一端口。

Stella 当前 `deploy/llama.py` 使用 embedding 模式启动内置服务，并以 `/v1/models` 检查端点。此事实来自源码，不代表已定位断连原因。进程存在、HTTP可达和实际推理成功必须分别记录。

## R01：复现与归因

在用户明确指出故障实例后，先绑定 STELLA_HOME、管理者PID/解释器、组件配置、目标端点、模型/二进制版本。读取该实例日志与客户端 trace，保留断连前后时间线，区分连接拒绝、超时、HTTP错误、模型加载、响应畸形与进程退出。先只读，不运行第二条启动路径。

使用隔离 fixture 复现：错误端口、端口被其他服务占用、进程活但推理卡死、模型列表可读但 embedding 失败、短暂断网、进程退出、OOM/资源压力。实际 OOM 实验只能在可控隔离环境进行。

产物：`runtime-diagnosis.json` 与时间线，至少给出失败边界、服务端与客户端证据、确定原因/未确定原因、复现命令。没有复现不编造根因。

## R02：恢复机制

- 健康字段：`process_alive`、`http_ready`、`inference_ready`、`last_success_at`、`failure_kind`、`consecutive_failures`、`restart_count`。外部服务的进程状态允许 unknown。
- 客户端复用连接池，区分 connect/read/pool timeout；禁无限重试，故障时快速返回可解释降级。
- embedding 等无副作用调用允许最多一次有 jitter 的短重试，但不得跨越请求总 deadline。Codex提交、配置写入、数据库事务不得套用此重试策略。
- 推理健康探针使用固定、无用户数据的最小输入，校验输出维度、有限数值与所期望的模型身份。探针频率有上限，避免 GPU忙时加重压力。
- 唯一管理者执行熔断与恢复：连续失败触发冷却；半开探针成功后恢复。重启只针对可验证归属的本组件PID，附重启预算和退避；超过预算需要人工处理。
- PID复用、错误服务占端口或模型不匹配属于身份/配置错误，不应不停重启。停止前验证可执行路径、实例标识与管理关系。

## 验收矩阵

在 Windows 和一个 Linux 环境分别验证：启动期、运行期、恢复期、停止期；检查HTTP状态、推理产物、PID/端口归属和故障原因。每个场景记录 passed/failed/skipped/unknown，不以进程存活替代推理结果。

最低门禁：短暂故障恢复不创建第二实例；进程卡死能被inference探针识别；重启预算耗尽能停止自动恢复；真实副作用任务无重复提交；Alcor故障与llama故障互相隔离；正常停止不被watcher误拉起。

此工作包通过后才能声称解决已复现的那一类断连问题，不能由“拆出决策层”推导出“llama.cpp稳定性已经修复”。
